# trassa-agent

**Русский** · [English](README.en.md)

Агент для серверов, которыми управляют через **Trassa**. Это программа, которую Trassa ставит на ваш VPS. Она связывает сервер с панелью: передаёт метрики и журналы и выполняет операции, которые вы подтвердили в панели.

Исходный код открыт, чтобы любой мог проверить, что делается на его сервере.

> [!IMPORTANT]
> **Статус: в разработке.** Код агента и помощника есть, подписанных выпусков пока нет, установить агент нельзя. Ниже описано устройство — это обязательства, на которые опирается реализация.

---

## Что такое Trassa

Trassa — панель для своей сети серверов у любых хостеров. Все VPS видны в одном окне: что запущено, какая нагрузка, когда платить. Обычные задачи решаются без командной строки: обновления, firewall, бэкапы, перезапуск служб, выпуск приложения.

Trassa не хостинг и не VPN. Серверы остаются вашими, у вашего хостера. Trassa ими управляет.

## Зачем агент, если есть SSH

Можно было бы управлять серверами по SSH. Но тогда панели нужен постоянный root-доступ ко всем вашим серверам, и любая её уязвимость стала бы уязвимостью вашей инфраструктуры. Агент устроен иначе:

| | SSH из панели | trassa-agent |
|---|---|---|
| Кто инициирует соединение | Панель заходит на сервер | Сервер сам подключается к панели |
| Входящие порты | Нужен открытый SSH | Не нужны, работает за NAT |
| Что может выполнить панель | Любую команду под root | Только операции из фиксированного каталога |
| Если взломан канал или шлюз | Полный доступ к серверу | Без подписи панели ничего не выполнится |
| Ошибка в правилах сети или SSH | Сервер легко потерять | Агент сам вернёт прежнее состояние |

Работа руками тоже остаётся. Для неё в Trassa будет веб-терминал на короткоживущих SSH-сертификатах с записью сессий.

## Как устроен

### Два процесса

| Процесс | Пользователь | Что делает |
|---|---|---|
| `trassa-agent` | `trassa`, без привилегий | Держит соединение с панелью, собирает метрики и журналы, проверяет подписи операций |
| `trassa-helper` | `root` | Слушает только локальный Unix-сокет и выполняет операции из списка, зашитого в бинарник |

Сетевой процесс не имеет прав root. Процесс с правами root не выходит в сеть.

### Соединение

- Агент сам открывает исходящее соединение WSS на порт 443. Входящих портов он не открывает.
- Сообщения передаются в protobuf, схема лежит в [`proto/`](proto/).
- Пульс отправляется каждые 20 секунд. После обрыва агент переподключается с растущей задержкой, не реже раза в 60 секунд.

### Подписанные операции

Каждое действие на сервере — это операция определённого типа, например `firewall.apply`, `service.restart` или `packages.upgrade`. Панель подписывает её ключом Ed25519, который хранится отдельно от шлюза связи. Агент выполнит операцию, только если выполнены все условия:

- подпись верна;
- операция адресована именно этому серверу;
- срок действия не истёк (обычно 5 минут);
- одноразовый номер раньше не встречался;
- тип операции есть в каталоге, а параметры проходят проверку схемы.

### Риск, подтверждение и откат

| Класс | Примеры | Подтверждение в панели | Откат |
|---|---|---|---|
| `READ` | Сведения о системе, порты, журналы | Не нужно | — |
| `CHANGE` | Перезапуск службы, обновления безопасности, бэкап | Клик | Копия конфигурации или предыдущий выпуск |
| `DESTRUCTIVE` | Firewall, SSH и пользователи, восстановление из бэкапа, перезагрузка | Второй фактор | Обязателен |

Перед изменением агент сохраняет затронутые файлы. Если после изменения сети или SSH панель не подтвердила связь, агент сам вернёт прежнее состояние, даже без связи с панелью. После каждой операции агент проверяет результат: служба запущена, порт отвечает, вход по SSH работает.

### Произвольные команды

Выполнение любых команд (`exec.run`) по умолчанию **выключено**. Включить его можно только в файле `/etc/trassa/agent.toml` на самом сервере (`allow_exec = true`), панель этот файл изменить не может. Даже включённая, команда проходит жёсткие запреты:

- `curl | sh` и аналоги;
- запись в `authorized_keys`;
- отключение firewall и журналов.

Кроме того, каждый запуск нужно подтвердить, а в подписанной операции должен быть снапшот хостера. Файл должен принадлежать root и не быть доступен на запись группе и остальным, иначе команды остаются выключенными. Выключение действует сразу; после включения перезапустите `trassa-helper` и `trassa-agent`, чтобы панель увидела возможность. Оболочки нет: команда приходит списком слов (`argv`) и запускается напрямую, без конвейеров, подстановок и шаблонов; оболочки, интерпретаторы и программы, которые сами запускают команды (`sudo`, `env`, `xargs`, `find -exec`…), запрещены. Программа ищется в фиксированном `PATH`, запускается по полному пути после ссылок и только если это неизменённый файл пакета дистрибутива (сверка с md5sums dpkg) в `/usr/bin`, `/usr/sbin`, `/bin` или `/sbin`, а файл и каталоги принадлежат root. Секретные файлы системы (`/etc/shadow`, ключи хоста SSH, `/etc/ssl/private`, `/root/.ssh` и другие) в службе недоступны. Запуск — во временной службе systemd от выбранного пользователя: каталоги Trassa в ней недоступны, по таймауту (до 300 секунд) останавливаются все её процессы, вывод (до 256 КиБ) уходит в журнал операции с вычищенными секретами.

## Чего агент не делает по построению

- Не принимает входящие соединения.
- Не выполняет ничего без действительной подписи панели.
- Не знает токенов ваших хостеров: они хранятся только в панели.
- Не отправляет содержимое ваших файлов, кроме операций, которые явно для этого предназначены: чтения журналов по запросу и бэкапа.

## Поддерживаемые системы

Первая волна: Ubuntu 22.04 и 24.04, Debian 12 и 13, архитектуры amd64 и arm64. На других системах установщик остановится с понятным сообщением.

## Установка и удаление

Агент ставится одной командой, которую выдаёт панель Trassa:

1. Установщик скачивает бинарник и проверяет его подпись [minisign](https://jedisct1.github.io/minisign/) и контрольную сумму.
2. Агент создаёт ключ Ed25519 прямо на сервере.
3. Агент регистрируется по одноразовому токену, который живёт 15 минут.

Для хостеров без cloud-init панель может один раз поставить агент по SSH, используя ключ, который вы добавили сами.

Удаление выполняется из панели или командой `trassa-agent uninstall` на сервере. Агент остановит службы и удалит свои файлы и пользователя, сервер продолжит работать без Trassa.

Обновления подписаны и раскатываются волнами. Если новая версия не запустилась, агент вернётся к прежней. Версию можно закрепить.

## Вход со своего компьютера: `trassa`

`trassa` — программа для вашего компьютера (macOS, Linux, Windows), а не для сервера.

```
trassa login --url https://app.example.com   # код подтверждается в панели, токен — в системном хранилище ключей
trassa servers                               # ваши серверы и логины
trassa ssh web-1                             # терминал через Trassa: открытый порт SSH не нужен
trassa ssh --direct web-1                    # сертификат на 10 минут и системный ssh напрямую (macOS, Linux)
trassa logout                                # отозвать вход и удалить токен
```

Токен входа хранится в Keychain (macOS), Secret Service (Linux) или диспетчере учётных данных (Windows). Если хранилища нет, например на сервере без сеанса D-Bus, токен лежит в файле `credentials.json` с правами 0600 рядом с настройками. В режиме `--direct` ключ Ed25519 создаётся заново на каждый вход и живёт только в памяти. ssh получает его через свой агент `trassa` только для чтения, ключ хоста берётся из панели, файлы настроек ssh не читаются (`-F none`).

## Состав репозитория

| Путь | Что там |
|---|---|
| [`proto/trassa/agent/v1/`](proto/trassa/agent/v1/) | Контракт канала между агентом и панелью (protobuf) |
| `cmd/trassa-agent`, `cmd/trassa-helper` | Два процесса: сетевой без прав и root-помощник |
| `cmd/trassa`, `internal/cli` | Программа `trassa` для компьютера человека: вход по коду устройства (RFC 8628), токен в системном хранилище ключей, список серверов, вход на сервер через Trassa (WebSocket терминала) и `--direct` (временный ключ в памяти, сертификат на 10 минут, системный ssh) |
| `internal/channel`, `internal/identity`, `internal/enroll` | Перевод в другую панель (`agent.rebind`, E24): помощник меняет запись о регистрации с точкой отката и автовозвратом, проверка подписи сразу переходит на ключи новой панели; агент перечитывает запись перед каждым подключением, подключается к новому адресу с обычной проверкой TLS по системным корням и ждёт `SignedConfirm` этой операции, подписанный ключом новой панели. Сертификат не прошёл проверку, рукопожатие отклонено или три попытки подряд без связи — возврат сразу, иначе по сроку (60–600 с) с итогом `REBIND_ROLLED_BACK` и причиной. Канал WSS, ключ агента, регистрация |
| `internal/helper`, `internal/helperrpc`, `internal/ops`, `internal/nonce` | Помощник: сокет с проверкой uid, зашитый список операций, проверки подписи, сроков и одноразовых номеров |
| `internal/rollback`, `internal/autorollback` | Точка отката и автооткат по таймеру systemd |
| `internal/metrics` | Метрики сервера из `/proc` и `statfs` без прав root: пачки раз в 15 с, без связи копятся до 10 минут |
| `internal/security` (детектор) | Наблюдение в помощнике: новые ключи, задания, юниты, SUID-файлы, пользователи, процесс из /tmp, подгрузка библиотеки, исходящие на подозрительные порты, долгая нагрузка CPU — событие не чаще раза в час; «Это сделал я» — `security.baseline.accept` |
| `internal/wireguard` | Приватная сеть (WireGuard): ключ создаёт помощник и не отдаёт, интерфейс через netlink и wgctrl, файл желаемого состояния как источник истины, пересылка только на интерфейсе сети, блок имён в `/etc/hosts`, на хабе с Docker — одно правило `DOCKER-USER`, автооткат |
| `internal/opcheck`, `internal/netcheck` | Проверки подписанной операции (общие для помощника и агента); `net.check` — проверка связи одним TCP-соединением, исполняет агент без прав |
| `internal/security` | Центр безопасности: `security.scan` — проверки только чтением из зашитого списка (SSH, пользователи, права, порты, firewall, обновления, диски, сертификаты, ядро, Docker), `packages.list_updates` — обновления из кэша apt без сети |
| `internal/remedy` | Исправления E18: `service.restart` и `service.start` для службы systemd или контейнера Docker (контейнеры Trassa — нет) с проверкой «работает 60 секунд тем же процессом»; `disk.cleanup` — только восстановимое (архив журнала по возрасту, кэш apt при свободной блокировке, образы без контейнеров кроме образов Trassa, кэш сборки), тома не трогаются никогда; `cert.renew` — certbot по имени с точкой отката (настройки продления и прежние ссылки); события `container.down` и `cert.expiring`; `app.unhealthy` (`firing`/`resolved`, причина `HEALTHCHECK`, `RESTARTING` или `MISSING`) — по контейнерам приложения Trassa раз в минуту, после 3 нездоровых опросов подряд и снятие после 2 здоровых, правило состояния общее с панелью (`proto/testdata/app-health.json`) |
| `internal/fsinspect` | Чтение для ИИ-оператора (E20): `disk.usage` — занятое место как `du -x` от «/» или корня из зашитого списка, глубина до 3, до 20 записей, ссылки не раскрываются; `config.read` — один файл до 64 КиБ из `/etc/nginx/**`, `/etc/systemd/system/*.service`, `/etc/docker/daemon.json` и compose приложений Trassa, без ключей, `.env`, `.htpasswd` и служб Trassa; путь после ссылок сверяется по открытому дескриптору, содержимое проходит фильтр секретов |
| `internal/helper/execpolicy`, `internal/helper/execrun` | `exec.run` (E20): флаг `allow_exec` из `/etc/trassa/agent.toml` проверяется раньше всего, `argv` без оболочки, запреты R28 — те же правила, что в панели (общий набор `proto/testdata/exec-policy.json`), плюс пути после ссылок; запуск — `systemd-run` с полным путём программы, пользователем, каталогом, таймаутом и пределом вывода |
| `internal/vpnprobe` | Точка замера VPN-пакета (E25): `vpn.probe.ensure` ставит Xray-core из зашитой таблицы (скачивает агент, помощник сверяет sha256), `vpn.probe.run` — замер цепочки по тестовому доступу: доступ расшифровывает помощник, конфигурацию движка строит сам из ссылки vless/trojan/ss (один выход на закреплённый IP из `allowed_endpoints`, вход socks только на 127.0.0.1), движок работает от отдельного пользователя `trassa-vpnprobe` во временной службе systemd без возможностей, с фильтром IP, скрытыми каталогами Trassa и пределами памяти и времени |
| `internal/backup` | Бэкапы restic (E13): restic скачивает агент, помощник сверяет sha256 из подписанной операции и ставит; секреты приходят зашифрованными HPKE на ключ помощника и хранятся в `/etc/trassa/backup/<plan>/` (root, 0600); снимок на каждый источник (пути, тома Docker — на ходу или с остановкой контейнеров тома и их запуском при любом исходе, в том числе после падения помощника, дампы PostgreSQL и MySQL потоком без файла на диске), проверка (`check` с выборкой, пробное восстановление, читаемость дампов), восстановление во временный каталог, на место с локальной копией и самостоятельным откатом или в каталог на этом сервере; цель SERVER — ключ источника только добавляет копии (принудительная команда `rclone serve restic --stdio --append-only` по SSH, ключ хоста цели закреплён), удаление копий — только `backup.prune` на самой цели; метрика `backup_last_success_age_seconds` по файлу, который ведёт помощник. Долгие операции идут своей очередью, не задерживая автооткат |
| `internal/logsrc`, `internal/logs` | Журналы по подписанной `logs.subscribe`: читает помощник (journald без оболочки, файлы только внутри `/var/log/` без ссылок, контейнеры через Docker API, приложение Trassa (`APP`) — все его контейнеры по метке `trassa.app_id`, включая прежние релизы), секреты вычищаются до выхода из root; агент копит пачки до 50 МБ и шлёт до квитанции. `logs.read` — последние строки по запросу. Память и CPU приложений (`app_mem_used_bytes`, `app_cpu_usage_percent` с меткой `app_id`) считает помощник по статистике Docker и отдаёт агенту вызовом `app.stats` |
| `internal/events`, `internal/queue` | Локальные пороги (служба упала, диск от 90%, память от 95% дольше минуты) и доставка кадров с квитанцией шлюза |
| `internal/update`, `internal/uninstall`, `internal/redact`, `internal/sysinfo` | Обновление по подписи minisign, удаление, очистка секретов в выводе, сведения о системе |
| [`scripts/install.sh`](scripts/install.sh), [`packaging/systemd/`](packaging/systemd/) | Установщик и службы |
| `test/stubpanel`, `scripts/ci-matrix.sh`, `tools/release-sign`, `scripts/release-gate.sh` | Матрица ОС в CI на заглушке панели, подпись выпуска и проверка перед публикацией |

Обновление скачивает сетевой процесс; помощник в сеть не выходит, он только проверяет подпись и суммы скачанного и ставит бинарники.

Сборка и проверки: Go 1.26, `make tools`, затем `make check` (генерат protobuf, `go vet`, staticcheck, тесты в обычной сборке и со служебным тегом `testops`, проверка выпускного бинарника, сборка `trassa` под macOS, Linux и Windows). Тестовая операция `test.config_write` есть только в сборке с тегом `testops`; `make release-check` проверяет, что в выпускном бинарнике её нет. В CI на каждый коммит: матрица ОС (Ubuntu 22.04 и 24.04, Debian 12 и 13 на amd64 и arm64 в контейнерах с systemd: установка командой панели, отказ при испорченной подписи, выход на связь, `system.info`, повторная установка, удаление; отчёт — артефакт `matrix-report-*`) и сборка выпуска на двух исполнителях со сравнением `sha256`.

## Проверить выпуск

Выпуск собирается воспроизводимо: из того же тега любой получает те же байты.

```sh
git clone https://github.com/NogMeer/trassa-agent && cd trassa-agent
git checkout v1.2.3
make release VERSION=1.2.3    # нужен Go 1.26+; точную версию компилятора из go.mod он скачает сам (GOTOOLCHAIN=auto)
diff dist/SHA256SUMS <(curl -fsSL https://github.com/NogMeer/trassa-agent/releases/download/v1.2.3/SHA256SUMS)
```

Подпись файла `SHA256SUMS` — [minisign](https://jedisct1.github.io/minisign/), ключи — в `TRASSA_RELEASE_KEYS` в [`scripts/install.sh`](scripts/install.sh):

```sh
minisign -V -P <ключ> -m SHA256SUMS    # доверенный комментарий: trassa-agent 1.2.3
sha256sum -c SHA256SUMS
```

Выпуск без подписи не публикуется: `scripts/release-gate.sh` проверяет её тем же кодом и ключами, что `install.sh`. Пока владелец не внёс ключи, список пуст, и установка и обновление намеренно отказывают.
